# Business knowledge dashboard

`/dashboard` uses Supabase email/password authentication. All knowledge reads and writes use the signed-in user's JWT and existing database RLS. Only owners/admins can save; agents/viewers can read. Public signup does not grant tenant membership, and the page exposes no service credentials. Before deploying the Save/Delete editor, apply the forward migration `202609150001_faq_deletion.sql` once. It adds a nullable deletion marker and a constraint preventing deleted FAQs from being published; existing records are preserved. Do not replay the foundation or reset the database. The inbox extension requires `202609130001_inbox.sql`; see `INBOX.md`.

Set `SUPABASE_PUBLISHABLE_KEY` to the project's `sb_publishable_...` key in Vercel Production and redeploy. `SUPABASE_URL` already exists. The dashboard passes only these public connection values to its browser component. For local development, set the public key in `.env.local` as well. OpenAI keys belong in server-side Vercel configuration for hosted AI use; a local copy is only needed for local AI execution. See `BOUNDED-AI.md` for the bounded AI mode and its deployment switch.

Before client access, create the approved owner account through Supabase Auth and assign it an `owner` row in `tenant_memberships` for the intended business. Do not grant access based solely on a browser-supplied email or tenant ID. No account creation or email sending happens automatically in the app. Client provisioning is currently an administrator operation; there is no invite-management UI. Do not commit account addresses or passwords. Users sign in with the password established privately during provisioning.

The dashboard presents twelve starter FAQs with blank answers, plus a blank first branch with name, city, street address, working hours and an optional Google Maps URL. Each branch also has BTC and Maintenance switches, both off by default. Enabling BTC reveals required BTC working-hours and phone fields; enabling Maintenance reveals required maintenance working hours. Legacy closing-day, general-phone and coordinate values remain readable in stored JSON but are no longer shown in the editor. Users can add more branches/questions. Business knowledge has one English source of truth; the assistant detects each customer's language and translates the approved information at reply time. Arabic text entered in editable fields still receives automatic text direction. Starter records are materialized on save or deletion; deterministic tenant IDs prevent duplicate starter saves. Unsaved changes are warned about when changing businesses, signing out or leaving the page.

Each entry offers Save and Delete. Save approves a completed entry for assistant use. Delete asks for confirmation, removes saved branches, and clears FAQ content while retaining a deletion marker so starter questions cannot reappear after reload. In-progress edits leave the prior saved version in place until saved. Blank FAQ answers cannot be approved through the editor. A branch needs a name, address and working hours to be approved; its Maps link can remain blank. An enabled BTC service also requires BTC hours and a phone number, while enabled maintenance requires its own hours. The retrieval adapter defensively excludes empty answers and incomplete branch entries, including records written outside this UI. Existing non-branch business facts are preserved.

Saved branches can be reordered vertically with the drag handle or the accessible up/down controls. The visible numbers update immediately, and every completed move is persisted automatically through the tenant-scoped `reorder_branches` transaction—there is no separate Save action for ordering. A newly added branch must be saved once before the list can be reordered. Migration `202610040002_branch_order.sql` introduced persisted ordering; `202610120001_single_knowledge_catalog.sql` preserves the English order while removing locale-specific ordering. Reordering remains restricted to owners/admins. The assistant reads this stored order on every new request, so jewelry, BTC, maintenance and nearest-branch lists use the same sequence shown in the dashboard.

Knowledge uses the existing `faqs` table and `business_facts` with category `branch`, unique tenant-scoped `branch:<uuid>` keys and JSON values. Migration `202610120001_single_knowledge_catalog.sql` deletes the retired non-English copies, removes both locale columns, and changes branch ordering to operate on the tenant's single catalog. All other knowledge categories remain untouched. Saves are per entry. Concurrent edits use last-save-wins; audited revisions/conflict resolution and recovery UI are future work. Dashboard approval makes records available to the bounded AI strategy when AI mode is enabled; echo remains the default diagnostic mode.

The sidebar also links to `/dashboard/inbox` for conversation history, delivery status, audited pause/resume and manual replies. Knowledge approval remains limited to owners/admins, while inbox controls also allow agents.

The password-change form requires at least six characters, matching Supabase's minimum supported password length. Four-character passwords are not supported by the hosted provider. This changes validation for future password updates, not existing account passwords.
