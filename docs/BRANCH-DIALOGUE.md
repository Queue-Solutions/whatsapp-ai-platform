# Branch navigation and conversation continuations

The assistant asks whether the customer wants jewelry or BTC/bullion before branch navigation when their product choice is unknown. A greeting also asks this question. The latest explicit customer choice takes precedence over earlier choices. Assistant offers do not count as customer choices.

Jewelry directories display branch names and saved cities, followed by an invitation to select a branch. The branch editor now includes an optional city field; existing JSON branch records remain valid. Missing cities are not invented. For an unambiguous selected jewelry branch, the application returns its saved address and map link directly. Multiple branches in a city stay a directory. Missing map links are acknowledged explicitly.

BTC availability and service hours come from approved FAQs. Retrieval prioritizes those FAQs and omits general branch hours from model-visible branch records for BTC questions. Addresses come from branch records when the customer requests a selected branch's location. Directory requests hide addresses, phones and map links from model-visible branch records. BTC branch lists and selected-branch details are rendered directly from a validated FAQ catalog, without model generation. Other BTC model requests exclude general directory FAQs and branch records outside that catalog.

Short replies accepting an offer resolve against the last assistant turn before retrieval. An acceptance of online links returns the relevant approved website/social links directly when available; an acceptance of branch help enters product routing. Contact collection does not treat online-shopping replies, common confirmations or known branch selections as names. History keeps a contiguous recent window of up to 16 messages and 9,000 UTF-8 bytes instead of skipping long replies and substituting older context.

The request byte ceiling is 22,000, below the existing 24,000 input-token allowance. Knowledge selection still checks the actual serialized request. The 650-token output allowance and durable reservations remain unchanged. Structured output limits prose to 1,000 characters, branch lines to 160 characters, and citations to supplied source labels. Link validation compares complete normalized approved URLs and handles Markdown delimiters and sentence punctuation.

The sidebar Blacklist indicator counts pending and kept blocks using authenticated membership RLS, fetching no message content. It refreshes every ten seconds, on window focus, and after a blacklist review. Removed blocks do not count; failed count requests show an unavailable indicator.

Read-only test-channel diagnostics on 2026-09-20 found four incomplete model responses, all using the full 650 output tokens, eleven invalid-source decisions and four unsupported-link decisions among the latest 108 AI requests. These counts identify failure categories, not the exact screenshot messages. No message bodies were read for these diagnostics. Regression tests use synthetic business records and conversation examples.

This change needs no SQL migration. It preserves existing chats, send deduplication, ambiguous-send handling, tenant isolation, test-number restrictions and the AI allowance. Hosted rollout and new test-number conversations are required to verify the changed model behavior in the running service.


## BTC continuity and silent recovery (2026-09-20)

Colloquial `سبايك` normalizes to `سبائك` throughout intent detection and branch routing. When the customer's recent context is BTC, asking for branches continues that choice instead of asking for jewelry/BTC again. BTC directories open with “لو بتسأل على السبائك، فدي الفروع المتاحة لخدمة BTC:” and retain FAQ-specific hours.

Arabic spellings of saved English branch and area names are normalized locally before matching, including `معادي`/Maadi and the common Korba, City Stars, Mivida, Kawthar, Nox, Arkan, ZIA, Kempinski and Senzo forms. A selection after the assistant's own jewelry/BTC directory heading retains that product context even when an earlier customer product word has fallen outside the bounded history. A unique selection returns the saved address and map deterministically without a model call, so retries or model inference cannot turn a known branch into a generic clarification or a false absence claim.

Collection, jewelry-viewing, website and social-account requests are fulfilled from approved FAQ URLs on the first request. This deterministic path does not make the customer confirm an offer in a second message, excludes map links, labels website/Instagram/Facebook destinations, and retains source-version validation before sending.

Technical failures never create customer-facing technical-error messages, including cached fallback decisions from earlier deployments. Recoverable model/network/validation failures get two additional internal attempts, with three- and seven-second silent backoffs, shorter response instructions and separate durable `:recovery:1` and `:recovery:2` reservations. All attempts retain normal budget accounting and source/link validation. If both attempts fail, or recovery cannot safely continue because of a permanent error, exhausted budget or still-running reservation, the application sends a fixed local continuity reply with no business claims. The inbound message is therefore not silently suppressed or marked as an unanswered AI reply. WhatsApp sends and uncertain send outcomes are never retried by this mechanism.

Legacy technical decisions passed directly to the repository still use the lease-validated suppression and dashboard-review path, so older deployments and cached records fail safely. The current strategy converts those decisions to the local continuity reply before persistence. Active complaints, existing reviews and human takeovers remain protected by the database send-intent checks. No new SQL migration or grant change is required.


## Enforced BTC branch catalog

The approved FAQ question “What information can you provide about your bullion or BTC products?” is preferred as the BTC catalog source. Its displayed position (question 8) is not used as an ID. Branch eligibility and the BTC-specific phone come exclusively from its `Branch name: phone` rows; service hours come from its BTC hours line. Names and phone numbers are read afresh for each reply, not hardcoded. Other branches in the menu cannot expand this list.

BTC directory replies are built directly from these rows with one introduction, one selection instruction, and no street addresses, map links or phone directory. A selected branch combines the FAQ's BTC phone/hours with the uniquely matching branch-menu address/mapsUrl. Name matching supports case/spacing, parenthetical location suffixes, and identity aliases such as Korba/Corba and Mansoura/MANS. A shared city does not establish a branch identity. Missing or ambiguous address matches are disclosed while preserving the confirmed BTC phone; another branch's address is never substituted.

Malformed or conflicting catalogs require a knowledge review instead of falling back to the jewelry directory. Multiple candidate catalogs must agree on the branch-to-phone mapping. Source IDs and versions accompany every deterministic reply for the existing pre-send tenant/publication checks. The rest of the model pipeline retains bounded recovery, while BTC directory/detail replies need no paid model call. No database migration is required.

## Nearest branches (2026-09-20)

Nearest/closest/near me/أقرب follow-ups now enter a dedicated location flow before branch-name matching or model generation. The immediate city/pin answer is an origin, not a branch selection. Unknown product intent is clarified first; the original nearest request or native pin survives that clarification. Generic words such as “city”, “town” and “new” cannot select a branch.

In AI mode, typed origins are semantically extracted from natural English, Arabic and misspelled sentences. The classifier returns an exact evidence span from the latest message and a corrected standalone place name. The backend accepts the correction only when the evidence really occurs in that message and both names remain textually similar. A bounded English/Arabic parser remains an outage fallback. Only the validated place name is sent to the geocoder, whose existing exact-name and single-result checks still reject similar businesses, conflicting places and unresolved text instead of guessing.

Native WhatsApp location payloads are range-validated and stored as a `geo:latitude,longitude` body with their original `location` message type through the unchanged authenticated, deduplicated ingestion path. Arbitrary location names/addresses are not retained. Text coordinates and HTTPS Google Maps pins are supported. Branches can save optional latitude/longitude together in the existing JSON record, or use actual place coordinates resolved from their saved Maps link. Viewport coordinates are not treated as pins. Short-link resolution checks every redirect against the Google Maps allowlist, has a five-second total deadline and at most four hops, and never forwards credentials.

City/area names are geocoded through a replaceable `LocationResolver`. `GEOCODER_URL` defaults to Photon’s public demo endpoint for this low-volume test-number foundation. Only the short location query and a bounding box derived from branch coordinates are submitted, never conversation history, customer identifiers or exact customer pins. It filters settlement types and requires one matching area name; ambiguity, throttling or unavailable geocoding asks for a pin. Photon has no availability guarantee; configure a dedicated Photon-compatible endpoint before scaling. Public map results and area lookups use bounded process-local caches. Reference: https://github.com/komoot/photon/blob/master/README.md and docs/api-v1.md.

Haversine distance sorts eligible branch coordinates. BTC candidates come exclusively from the current FAQ catalog and unique branch-menu joins; jewelry uses approved branch records. Results show up to three names/cities/distances with a selection instruction, followed by the existing saved-address/map/FAQ-phone flow when selected. City-centre distances are marked approximate, and all results distinguish straight-line distance from driving distance/time. Missing coordinates are disclosed as incomplete coverage, never evidence of the globally nearest branch. Compared source versions are revalidated by the existing pre-send guard. No business coordinates, BTC eligibility or phone numbers are invented by the model.

The separate `202609200001_ai_capacity.sql` migration removes the obsolete $0.25 lifetime cap (NULL means uncapped) and supports 2,000 output tokens. This supersedes the historical capacity figures above; usage accounting, reservations, tenant isolation, uncertain-send handling and bounded model retries remain active.

## Catalog-driven semantic branch routing (2026-09-30)

Branch routing is based on the currently published branch catalog rather than fixed regional branch lists. The compact intent classifier receives each branch's label, name, city and address, and may select every relevant catalog label for a city or area. The backend combines a semantic directory selection with deterministic matches only when the semantic result contains every deterministic match; an explicit current branch or city therefore cannot be replaced by stale conversation context. Product context remains separate, so the same area can correctly yield different jewelry, BTC or maintenance sets.

Location matching now applies bounded typo tolerance to meaningful words from the live branch name, city and address. Canonical bilingual area equivalents remain normalization data, but customer misspellings do not require one-off entries. A request such as `fiftsh settlement` can therefore match the same published area records as `Fifth Settlement`, while unrelated short words and generic city terms cannot select a branch.

Structured city matches are categorical rather than relevance-ranked: when a requested city matches three approved branch records, all three remain in the result even if one address repeats the city name or contains more matching words. Exact saved branch-name matches still take priority, and address matching is used only when no structured city matches. When translated records describe the same physical branch, the preferred-language record remains customer-facing while the paired record's name, city and address are retained as search-only metadata. This makes Arabic and English area requests consistent when one translation has a blank city field, without displaying fields from the wrong language or inventing locations.

Plural continuations such as “both”, “send their locations”, `هما الاتنين` and `مواقعهم` resolve the branch identities in the most recent assistant directory and return every requested saved address and map link. For BTC, those records are intersected with the current FAQ-derived eligibility catalog before details are rendered, preserving the FAQ as the authority for service availability and phone numbers. Jewelry branch facts come from the saved records. No address, branch membership or map link is produced by the model.

Branch directories are deliberately compact: they contain only a numbered branch name and saved city in dashboard order. Addresses, map links and phones appear only after the customer selects one branch, or explicitly asks for the details of multiple branches. Natural presentation corrections such as “just branch names”, “without addresses” and their Arabic equivalents keep the current product and branch context while switching back to the compact directory; they do not require a special command phrase.

The dashboard order is an explicit persisted property rather than an inference from creation time. Migration `202610040002_branch_order.sql` backfills the current sequence and exposes one owner/admin-only, tenant-and-locale-scoped transaction that accepts every branch exactly once. Dragging a saved branch or pressing its up/down controls writes the full order immediately; the next assistant request loads it without a restart. New branches are appended automatically. Missing legacy order values still fall back to the stable loaded order during a rolling deployment.

A number reply is resolved against the most recent numbered branch directory still present in the retained conversation window before semantic intent classification. That directory remains authoritative after an earlier numbered selection has returned branch details, so a later number selects the corresponding different branch instead of reusing the first selection or rebuilding the full list. Out-of-range numbers are clarified rather than guessed.

Deterministic branch replies lead with a short answer fitted to the actual request: all-branch directories say that they contain all branches, city-scoped directories name that city, and selected details name the chosen branch. They do not prepend a mandatory acknowledgment, claim the customer asked about “this area” when no area was supplied, or repeat “I understand you’re looking…” as a stock phrase. General model-generated replies follow the same direct-answer rule while retaining grounded-source validation.

Direct rendering no longer depends on a finite allowlist of acceptable sentence words. It distinguishes branch navigation from product-availability questions by intent and grammar, which allows ordinary Arabic/English questions about any city while preventing a product question that merely names a branch from being replaced by its address. Regression coverage includes New Cairo/Tagamo3 jewelry and BTC, Hurghada, misspelled English areas, bilingual city aliases, plural multi-location follow-ups and stale-classifier protection. This change needs no SQL migration.

Cancelling an active personal follow-up now clears its attention state instead of preserving a resolved ticket. The conversation transcript and audit event remain intact, the assistant resumes with a new automation epoch, queued paused messages stay skipped, and follow-up/contact fields are cleared. Migration `202609300002_cancel_clears_attention.sql` also removes only the historical resolved cards carrying the exact former cancellation summary; it does not delete conversations, messages, ordinary resolved issues or complaints.
