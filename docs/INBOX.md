# Human inbox

`/dashboard/inbox` uses the existing Supabase sign-in. The client can filter all conversations, Needs attention, Complaints and Resolved. Lists load 50 conversations at a time, with Load more and server-side filtering so older waiting cases are not hidden. Counts cover the full tenant. The inbox shows the latest 100 messages (load older up to 500), delivery status and recent conversation activity. The page polls every ten seconds. Owners, admins and agents can pause/resume or send replies; viewers remain read-only. Private message text is rendered as plain React text, never HTML, and is not logged.

Apply `202609130001_inbox.sql` and then the forward migration `202609160001_inbox_attention.sql` once before deploying this version. The latter adds attention state, reason, summary, timestamps and complaint labels; it preserves messages and business knowledge and brings existing open paused conversations into Needs attention. It adds conversation epochs, audited mode events and durable manual-send requests. It does not alter existing message bodies or business answers, broaden direct table mutation grants, or reset the AI budget. As with earlier SQL Editor migrations, do not replay the foundation or assume the CLI migration history was updated.

`set_conversation_mode` is a narrow security-definer function using the authenticated membership and a version check. It updates only the selected open conversation and adds an audit event with the actor. Browsers have no direct conversation update permission. Each pause/resume increments an epoch; automatic jobs from before that boundary are suppressed even if the assistant has since resumed. New jobs inherit the current epoch. A paused assistant does not answer new greetings or business questions. The user must resume explicitly. Messages already being sent cannot be recalled, and the interface explains this when pausing.

A staff reply requires the assistant to be paused, an open conversation, a recent customer message (the same conservative 23-hour-55-minute window as automatic replies), the configured Meta test channel and an allowlisted recipient. The browser submits a fresh UUID request identity with its signed-in bearer token to `/api/dashboard/reply`; the handler verifies that token with Supabase Auth before constructing the privileged service. The database derives the tenant and destination from the conversation, checks the verified actor's membership again, and creates a durable sending intent before the existing Meta sender executes. The request cannot supply a destination number, tenant or actor override. No message is sent just by opening or pausing a conversation.

Repeated submission of an existing request identity returns its stored state and never sends again. A changed body with the same identity is rejected. Known provider rejection records failure. Network or settlement uncertainty records `needs_review`; abandoned sending intents are marked uncertain after two minutes by the existing worker. No automatic manual-send retries exist. The UI blocks the attempted draft and tells the operator to check the actual conversation before composing another reply. Delivery receipts are preserved even if they arrive before the provider send response.

Only text replies are supported in this version. Media bodies are represented by their message type; no attachments are downloaded. Team activity records mode changes and prepared manual replies, not message text. The dashboard shows an in-app attention notification and Inbox count, polling every ten seconds while open. Notifications do not send email, WhatsApp or operating-system alerts. Search, historical import, templates outside the reply window and in-app resolution of uncertain delivery remain future work. No staff assignments or team-routing UI is included.


## Single-client attention workflow

- Explicit personal-contact requests and high-signal complaints in English and Arabic are detected without a paid call. The bounded model can also classify contextual complaints when its knowledge and budget guards permit a call. Neutral policy questions must not be complaints. Automatic labels and summaries are suggestions to review against the messages; detection is not exhaustive. Media is not classified.
- Automatic handoff atomically prepares one acknowledgment, pauses automation, increments the generation epoch, and saves the attention reason/summary and audit event. A failed or uncertain acknowledgment leaves the case visible. Duplicate webhooks/jobs do not create duplicate cases or sends.
- Reply personally moves the case to In progress and keeps the assistant paused. Resolve moves it to Resolved and also keeps it paused. Return to assistant explicitly resumes only future messages. Complaint labels can be added or removed manually; removing one does not resume automation or resolve a case.
- A new inbound message after resolution reopens Needs attention and leaves the assistant paused. Duplicate or old delayed messages do not reopen it. Resolving never deletes or closes the underlying conversation. The Complaints filter includes both active and resolved complaints, with a visible status.
- `manage_conversation_attention` checks membership, permissions and the expected row version, and records changes. Direct browser UPDATE remains denied. All existing send allowlist, channel, service-window, durable deduplication and uncertain-delivery guards remain in force.
- Classification applies to new eligible AI-handled messages. Existing history is not retrospectively classified; already-paused conversations can be labeled by the client. AI summaries contain no promises of refunds, completed actions or response times.
