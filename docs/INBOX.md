# Human inbox

`/dashboard/inbox` uses the existing Supabase sign-in. The client can filter all conversations, Needs attention, Complaints and Resolved. Lists load 50 conversations at a time, with Load more and server-side filtering so older waiting cases are not hidden. Counts cover the full tenant. The inbox shows the latest 100 messages (load older up to 500), delivery status and recent conversation activity. The page polls every ten seconds. Owners, admins and agents can pause/resume or send replies; viewers remain read-only for those conversation actions. Every signed-in tenant member can set business-wide assistant availability because the current dashboard is intentionally shared only with authorized operators. Private message text is rendered as plain React text, never HTML, and is not logged.

## Assistant availability

Apply `202609220001_assistant_availability.sql`, `202609230001_conversation_controls.sql`, and then `202609240001_customer_resume.sql` once before deploying the matching application. The Inbox offers **Assistant on**, **Assistant off**, and **Selected chats only**. Off and unselected conversations still receive and store inbound messages, but their automatic jobs are skipped before moderation or a paid model call. Per-conversation personal takeover, blacklist, channel, service-window and send guards still take precedence when the business-wide setting permits a reply.

Availability changes are made through a tenant-scoped security-definer RPC; browsers have read-only table access and cannot update channels or selections directly. Each change is audited without copying message content. A change increments open-conversation epochs and suppresses pending jobs so old messages are never replayed after re-enabling the assistant. Processing work is checked again in the application and at the durable send-intent transaction. A provider send already in flight cannot be recalled, which the interface states.

Apply `202609130001_inbox.sql` and then the forward migration `202609160001_inbox_attention.sql` once before deploying this version. The latter adds attention state, reason, summary, timestamps and complaint labels; it preserves messages and business knowledge and brings existing open paused conversations into Needs attention. It adds conversation epochs, audited mode events and durable manual-send requests. It does not alter existing message bodies or business answers, broaden direct table mutation grants, or reset the AI budget. As with earlier SQL Editor migrations, do not replay the foundation or assume the CLI migration history was updated.

`set_conversation_mode` is a narrow security-definer function using the authenticated membership and a version check. It updates only the selected open conversation and adds an audit event with the actor. Browsers have no direct conversation update permission. Each pause/resume increments an epoch; automatic jobs from before that boundary are suppressed even if the assistant has since resumed. New jobs inherit the current epoch. Pausing a normal chat does not create a Needs attention case. A paused assistant does not answer new greetings or business questions. The user must resume explicitly. Messages already being sent cannot be recalled, and the interface explains this when pausing.

A staff reply requires the assistant to be paused, an open conversation, a recent customer message (the same conservative 23-hour-55-minute window as automatic replies), the configured Meta test channel and an allowlisted recipient. The browser submits a fresh UUID request identity with its signed-in bearer token to `/api/dashboard/reply`; the handler verifies that token with Supabase Auth before constructing the privileged service. The database derives the tenant and destination from the conversation, checks the verified actor's membership again, and creates a durable sending intent before the existing Meta sender executes. The request cannot supply a destination number, tenant or actor override. No message is sent just by opening or pausing a conversation.

Repeated submission of an existing request identity returns its stored state and never sends again. A changed body with the same identity is rejected. Known provider rejection records failure. Network or settlement uncertainty records `needs_review`; abandoned sending intents are marked uncertain after two minutes by the existing worker. No automatic manual-send retries exist. The UI blocks the attempted draft and tells the operator to check the actual conversation before composing another reply. Delivery receipts are preserved even if they arrive before the provider send response.

Only text replies are supported in this version. Media bodies are represented by their message type; no attachments are downloaded. Team activity records mode changes and prepared manual replies, not message text. The dashboard shows an in-app attention notification and Inbox count, polling every ten seconds while open. Notifications do not send email, WhatsApp or operating-system alerts. Search, historical import, templates outside the reply window and in-app resolution of uncertain delivery remain future work. No staff assignments or team-routing UI is included.


## Single-client attention workflow

- Explicit personal-contact requests and complaints in English or Arabic are classified semantically before business routing, so misspellings and changed word order do not depend on exact phrases. The backend—not the model—starts contact collection and human takeover. A conservative local detector is retained only when semantic classification is unavailable. Neutral policy questions must not be complaints. Automatic labels and summaries are suggestions to review against the messages; media is not classified.
- Detected issues start personal contact collection, described below. The conversation enters Needs attention immediately. The assistant pauses after collecting both details, or if the customer declines. A failed or uncertain reply leaves the case visible. Duplicate webhooks/jobs do not create duplicate cases or sends.
- The customer may provide the requested name and phone number together or in separate messages. A refusal pauses for staff review without inventing contact details, while a new business question leaves the form and follows normal business routing. After completed collection, the acknowledgement states that the assistant is off and that IRAM will make contact within 24 hours. An exact standalone `AI` or `Cancel` message cancels an active personal follow-up or complaint, clears its contact form and complaint label, records an audit event, and returns that chat to automatic mode. Pending messages accumulated during the pause are never replayed. Business-wide assistant availability still takes precedence.
- A normal chat shows **Reply personally** plus a per-chat **Pause assistant** control (or **Resume assistant** while paused). An active issue shows only **Reply personally** and **Resolve**. Reply personally moves the case to In progress and keeps the assistant paused. Resolve atomically marks the issue Resolved and returns that chat to automatic mode; the business-wide master availability setting still takes precedence.
- An ordinary new inbound message after resolution does not recreate an issue. A newly detected complaint, human request or missing answer can create a fresh Needs attention case. Duplicate or old delayed messages do not reopen it. Resolving never deletes or closes the underlying conversation. The Complaints filter includes both active and resolved complaints, with a visible status.
- `manage_conversation_attention` checks membership, permissions and the expected row version, and records changes. Direct browser UPDATE remains denied. All existing send allowlist, channel, service-window, durable deduplication and uncertain-delivery guards remain in force.
- Classification applies to new eligible AI-handled messages. Existing history is not retrospectively classified; already-paused conversations can be labeled by the client. AI summaries contain no promises of refunds, completed actions or response times.


## Missing business information

The `knowledge_gap` model action identifies a clear business question that the supplied approved sources cannot answer. Ambiguous questions should receive one clarification first, using recent history to avoid repeating it. Unrelated requests, prompt injection, provider/knowledge-load failures, exhausted budgets and source-validation failures do not create knowledge gaps. When no approved knowledge is published, a substantive text question receives a deterministic review flag without a paid call. The model's short explanation is an assessment of the supplied sources, not proof that every saved source lacks the answer. When retrieval omits records, the explanation explicitly says other saved knowledge may contain it.

The strategy maps a gap to reason `missing_business_information` and begins contact collection. `prepare_followup_reply` records the contact state, reply intent, `knowledge_gap` attention reason, explanation and exact inbound `attention_message_id` together after the existing send guards. The flag persists even if delivery fails or is uncertain. While collecting details the assistant can still answer known questions. The original issue and waiting time survive contact replies. A new complaint takes priority over a knowledge gap and updates its explanation and message reference.

Resolving a gap returns the chat to automatic mode. Ordinary new messages do not reopen a resolved review; another knowledge gap does. The master availability setting and all normal eligibility guards still apply, and no old unanswered messages are replayed.

The Inbox shows the explanation, exact question and suggested next step. Owners/admins can open **Add to FAQs**, edit the question, provide a confirmed answer and choose its language. The FAQ is published only on **Save FAQ**, using authenticated RLS-protected writes and a tenant/message-scoped stable ID so retries do not duplicate it. A previously deleted FAQ is not silently recreated. **Prepare personal reply** pauses the assistant and fills the composer; the owner must explicitly press **Send reply**. Saving a FAQ alone does not send a message or resolve the review. Questions and explanations are customer data and must never be written to application logs.

## Personal contact collection and reply style

English and Arabic greetings always write the brand as uppercase English `IRAM`. Generated replies use short paragraphs and tasteful emojis. Each branch is returned as a separate structured list item and rendered on its own line with a blank line between entries. A final formatter converts Arabic or inconsistently cased brand spellings to `IRAM` and removes English/Arabic semicolons, including safely encoding those characters inside URLs. Sources and customer messages themselves are unchanged.

For complaints, explicit human requests, unsupported business actions and confirmed knowledge gaps:

1. Add the conversation to Needs attention with the issue explanation and ask for the customer's name and preferred contact number. Only explicitly supplied details are collected, never inferred from the WhatsApp profile. Order numbers must not be treated as callback numbers.
2. Accept either detail first and ask only for the missing detail. Normalize Arabic/Persian digits and Egyptian local numbers. International numbers need a country code. This local collection step uses no paid model call. A new business question can still use normal knowledge handling.
3. Persist both details together with a single acknowledgment intent, then tell the customer someone from IRAM will contact them personally shortly. Pause the assistant and invalidate older jobs. The Inbox **Personal follow-up** card shows the supplied name and a clickable phone number. The number is for the owner to contact personally and never replaces the original WhatsApp send destination or its allowlist checks.
4. If the customer declines, keep the case visible and pause for a personal reply here without promising a callback. Resolving stops unfinished collection and returns the chat to automatic mode, while message history remains.

The owner must monitor the Inbox and fulfill the promised personal follow-up. This does not place a call or send an external notification. A prepared acknowledgment is not proof of delivery: check its delivery status, especially for failed/uncertain sends. Technical failures, off-topic requests and prompt injection retain their separate guarded responses instead of being mislabeled as missing business information. Existing paused conversations stay paused.
