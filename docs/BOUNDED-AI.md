# Bounded AI replies

The strategy uses the pinned `gpt-5.4-mini-2026-03-17` snapshot through the Responses API with strict JSON output, `store:false`, no tools and `reasoning.effort: none`. The explicit no-reasoning setting preserves low latency for the two bounded customer-support tasks. Semantic classification has a 600-token output cap and eight-second timeout. Grounded answer generation has a 2,000-token output cap, a 12-second initial timeout and at most two separately reserved recovery attempts after three- and seven-second silent backoffs; recovery calls use eight-second timeouts. This leaves time inside the 60-second worker deadline to persist and send the model-independent continuity reply if every model attempt fails. Official model pricing checked 2026-09-28: $0.75 per million input tokens and $4.50 per million output tokens. Cached inputs are conservatively costed at the full input rate in this application's ledger. This ledger is a model-cost estimate, not an OpenAI account billing report.

Sources: [model and pricing](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [latest-model migration](https://developers.openai.com/api/docs/guides/latest-model), [Responses API migration](https://developers.openai.com/api/docs/guides/migrate-to-responses).

## Configuration and release order

1. Apply the forward migrations in order through `supabase/migrations/202609280001_gpt_5_4_mini.sql` before deploying the new application code. Existing installations that already have the earlier migrations need only apply the unapplied forward migrations. Do not replay the baseline or reset the database. SQL Editor application does not populate CLI migration history.
2. Set server-only `OPENAI_API_KEY` in Vercel Production. A local copy is only needed for local AI execution. Never add a public prefix or put the key in chat, source control or browser code.
3. Leave `WHATSAPP_REPLY_MODE=echo` (the default) during initial acceptance. Set `AI_ACCEPTANCE_ENABLED=true` temporarily and deploy to run the protected fixed-fixture checks below.
4. After acceptance, set `AI_ACCEPTANCE_ENABLED=false` and `WHATSAPP_REPLY_MODE=ai`, then redeploy. Mode changes require a deployment to affect the hosted runtime. Echo remains available for diagnostics.

## Approved knowledge and conversations

Each inbound message's tenant is resolved from the trusted test channel. For eligible new text, a semantic classifier first returns a strict intent, confidence, corrected query, language, product and approved branch labels. During active personal-contact collection it also returns an exact customer-name span and whether the customer reports a missed earlier follow-up. The backend rejects any proposed name that is not present verbatim in the current message or does not have a valid personal-name shape, so ordinary statements cannot be persisted as names. The classifier receives the latest message, bounded history, branch names/cities and FAQ questions, but no FAQ answers. This makes Egyptian Arabic, English, changed word order and ordinary misspellings model-understood instead of depending on a growing list of phrases. Classifier output is not a business fact: the backend validates branch labels and executes exact workflows from current database records. If classification is unavailable or below confidence, conservative local detection remains only as a resilience fallback; unclassified proposed names are never stored.

The strategy reads published facts/FAQs in both `en` and `ar`, excludes incomplete branches and blank FAQ answers, and lets the answer model understand paraphrases and translate supplied facts. Local retrieval ranks whole approved records using the classifier's corrected query, bilingual topic terms, question/branch names and recent customer context. Branch/location questions prioritize the branch directory. Complete multi-branch results are rendered from structured records, numbered in dashboard order, and can be selected by replying with their displayed number; the model cannot reorder or invent those records. Each answer request selects at most 40 sources and 8,500 UTF-8 bytes, and also checks the fully serialized 22,000-byte request bound while selecting. A larger saved corpus no longer disables all answers. Records are never truncated; oversized individual records are skipped. Coverage metadata tells the model when sources were omitted or the branch directory is incomplete, so it must not present partial lists as exhaustive and should ask for clarification when needed. Labels and revision timestamps remain intact, and cached citations are checked against the full current approved corpus. See `AI-ROUTING.md`.

Conversation history is a contiguous recent window bounded to 9,000 UTF-8 bytes. Future messages and uncertain outbound intents are excluded. Customer phone numbers, account credentials, tenant IDs and internal source IDs are not included in model input. Each serialized request is at most 22,000 UTF-8 bytes, with a conservative 24,000-input-token reservation including framing/schema margin. Oversized messages/context get a local unavailable response. `store:false` disables response storage for API retrieval; it does not promise zero provider retention.

Both prompts treat customer messages, history and catalog content as untrusted data. The classifier never answers and never receives FAQ answers. Business facts must come from approved sources, with structured source references. Unknown source labels and invented links are rejected. Human follow-up, complaints, online links, careers, repairs and branch details are executed deterministically after semantic classification. Greetings, thanks and direct questions about the assistant's identity are rendered from fixed nonfactual templates; identity replies do not require a knowledge citation or model retry. General business questions use a second grounded generation call. Provider, retrieval and budget failures never send a technical-issue message to the customer. Recoverable answer-generation/validation failures, including an unsolicited branch answer for a non-branch request, get up to two internal recovery attempts, using a quick three-second retry followed by a longer seven-second backoff; classification itself is durably recorded but not blindly retried. If verified recovery is exhausted, the application sends a fixed, model-independent continuity reply that makes no business claim and offers the supported service categories. It does not silently discard the customer's message or create an unanswered-reply review. Grounding and source validation reduce errors; they do not mathematically prove that every natural-language interpretation is correct, and external WhatsApp delivery itself cannot be guaranteed, so client-specific evaluation and delivery monitoring remain required.

Before an external reply, the existing database guard rechecks lease validity, human takeover, channel state and the service window. AI answers also recheck source publication and revision timestamps within the send-intent transaction. A changed or unpublished source suppresses that pending answer. An explicit human request records a handoff by setting the conversation to human mode together with its acknowledgement intent. The reply tells the user to contact the team directly; it does not claim that staff were notified. The dashboard inbox now provides audited pause/resume and manual replies for owners, admins and agents. It refreshes every ten seconds; external staff notifications are not implemented. Pausing or resuming invalidates earlier automatic jobs so they are not replayed. A send already in flight may still arrive. See `INBOX.md`.

## Usage accounting without the obsolete development cap

`202609200001_ai_capacity.sql` removes the old $0.25 lifetime allowance. `ai_budget.cap_nano = NULL` means uncapped; the owner manages available funds in OpenAI. `202609280001_gpt_5_4_mini.sql` adds the new model's reservation and settlement rates while retaining the previous snapshot and reservation sizes for rolling deployment and rollback. Apply both migrations before deploying the model upgrade. The ledger spans all requests/tenants using this deployment's database, including acceptance tests and real test-number AI replies. Only backend credentials can reserve or settle usage. Browsers can only read their own tenant's AI request records through RLS; they cannot change the budget, reservations or usage.

Before each GPT-5.4 mini call, a transaction reserves 27,000,000 nanodollars ($0.027): 24,000 input tokens at $0.75/M plus 2,000 output tokens at $4.50/M. Reservations serialize on the shared budget row. The compact classifier and any later answer generation are separate durably metered calls; deterministic intents normally stop after classification. A completed call settles to reported token usage and releases the excess reservation. Rollback calls using the previous GPT-4.1 mini snapshot still reserve and settle at their previous rates. No application spending cutoff applies while the cap is NULL.

Requests have a unique tenant-scoped key. Completed requests return their stored decision rather than call the model again. The same attempt key is never sent to OpenAI again. A recoverable failed/completed-invalid attempt permits up to two new reservations with stable `:recovery:1` and `:recovery:2` suffixes. The same resolved customer message, history and approved-source checks are reused; no synthetic customer message is inserted. Replayed jobs reuse those recovery results too. A still-reserved attempt, exhausted budget or permanent authentication/policy failure does not start or continue recovery. Timeouts, malformed usage or crashes retain the full reservation, so concurrent/recovery workers cannot silently overspend. Failed usage persistence prevents sending the uncommitted generated answer; a recovered worker can use a committed cached result or return a safe local fallback. Do not reset this allowance or uncertain reservations merely to retry tests. Increasing it again requires a new explicit user budget decision and a reviewed schema/configuration change. This is an application allowance; other apps or keys on the same OpenAI account are outside its control.

## Acceptance without WhatsApp sends

`POST /api/internal/ai-acceptance` requires the existing `CRON_SECRET` bearer credential, the explicit enable switch, and one body field: `case`. It resolves the development tenant from the configured test channel, accepts only the fixed case IDs in `src/modules/ai/acceptance.ts`, shares the same strategy/provider/ledger as messaging, and never invokes the WhatsApp sender or inserts customer messages or business knowledge. The source facts belong to a fictional test shop. An arbitrary query, tenant override or extra body field is rejected. Version-three cases use durable `acceptance:v3:<case>` identities.

Cases cover English/Arabic wording changes, missing prices, prompt injection, branch ambiguity, a contextual follow-up, empty knowledge and a human request. Return bodies contain fictional test replies and check results only; do not generalize that endpoint into a customer-message simulator. Disable the endpoint after testing. Real WhatsApp round trips with approved business content are a separate acceptance step and require the user to supply/approve that content first.
